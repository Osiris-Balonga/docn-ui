## Justification for added tests

Planned coverage is limited to catalog filtering, editor coordination, shared image validation, lifecycle cleanup, and one real catalog/playground journey. Existing schema, PDF, and business-card journeys will be reused instead of multiplying format, theme, MIME, or template permutations.

## Visual and document checks

The minimal, editorial, and Studio nominal PDFs were generated through the existing qualified Node renderer. Their first pages were rasterized at 144 DPI to 482×312, 511×284, and 505×288 PNG files, preserving each actual card proportion. The three files were inspected directly: distinct structures, accents, text, and card edges remain clear with no clipping. Their exact dimensions, source fixtures, page numbers, and hashes are recorded in the serializable catalog manifest; the gallery imports no React PDF composition or renderer.

S02 exposes the same shell on all three static detail routes while keeping the business-card form explicit. Example data imports use example-only package exports so the client editor does not pull a document composition barrel; the worker dynamically imports only the selected composition. The retained real browser journey proved the minimal route after this split. Accent changes are restricted to four validated PDF colors, and screen/print/print-with-marks map to the existing qualified print-profile contract.

S03 makes the minimal card's logo capability real. The browser checks byte signatures and size before decoding, applies EXIF orientation through `createImageBitmap`, enforces the decoded 16-megapixel limit, and re-encodes through canvas before retaining bytes in memory. The UI and worker create only scoped Blob URLs and revoke them on replacement/completion/unmount; PDF.js already cancels rendering and destroys its loading task on every change and unmount. Transferred request copies may detach without touching the retained normalized source buffer. The real journey reused a generated catalog PNG rather than adding another image fixture.

S04 keeps the boundary explicit. The unit test uses a constructed memory buffer and the real protocol parser; it does not decode or render. The component suite uses a simulated render session and covers form/request coordination only. The playground E2E uses the production static build, browser image decoder and canvas, actual Web Worker, React PDF renderer, PDF.js preview, browser download, and independent PDF.js inspection in the test process. Request observation found no third-party origin, request body, entered name, or user image URL. Blob-backed worker and download traffic is browser-local and does not cross the HTTP boundary.

The CI `e2e-chromium` job depends on `build`, downloads the static output plus its commit/input fingerprint, verifies it against the checkout, installs Chromium, and runs only Playwright. The root build writes the same fingerprint, and `test:all` reuses it only after verification. Standalone E2E still builds when no valid prepared artifact exists.
