## Scope

L11 completes G4 with fifteen distinct compositions across Business Cards, Event Tickets, Receipts, Labels, and Invoices. It adds a strict invoice contract, reusable flowing table primitives, Minimal, Business, and Subscription invoice layouts, A4/Letter portrait rendering, repeated headers and footers, deterministic receipt-shared monetary calculations, PDF-derived catalog previews, static routes, and four official shadcn registry items. Invoice source remains independent of the site and installs into the consumer's existing shadcn configuration.

After review, the maintainer requested a neutral shadcn-like starting point, more realistic billing specimens, a larger print preview, and enough source context to understand imported family components. Commit `2476124` makes all three bundled theme palettes monochrome by default while preserving typed font/accent overrides, introduces generic SaaS subscription invoice and receipt examples, regenerates all fifteen PDF-derived thumbnails, adds an enlarged preview dialog, and replaces the single-file drawer with a bounded template/family tree. The tree includes the entry, example, layout, schema, and plan while excluding metadata, index files, transitive primitives, and arbitrary repository access.

The billing structures were informed by official documentation for [Stripe invoice customization](https://docs.stripe.com/invoicing/customize), [Stripe's hosted invoice page](https://docs.stripe.com/invoicing/hosted-invoice-page), [Anthropic paid-plan invoices](https://support.anthropic.com/en/articles/8325618-paid-plan-billing-faqs), [Netflix printable invoices](https://help.netflix.com/en/node/23551), and [Spotify receipts](https://support.spotify.com/us/article/check-receipts/). No third-party name, logo, proprietary copy, or customer document is bundled; the examples use fictional identities and only reuse common billing information architecture.

## Justification for added tests

The invoice schema extends the existing unit scope because due-date ordering, duplicate identifiers, and explicit row-height limits are invoice-specific validation risks not covered by money tests. The existing invoice PDF file carries both the family nominal table and the single representative multipage risk; it does not cross formats, themes, locales, and line counts. One E2E file was required by the lot to prove the new family's direct route, previews, and source surface, but it does not duplicate monetary or pagination assertions from PDF tests. The existing consumer orchestration now splits the two qualified environments across distinct dependency closures instead of adding another external project or reinstalling all variants.

The reference-driven refinement adds no test case. It strengthens the existing minimal-invoice fixture with a unique project subtitle and moves the existing long-title Classic ticket fixture to the compact French layout. Two coordinate assertions prevent the observed venue/seat overlap. The existing two-sided business-card test continues to assert every contact field after the new two-column composition.

## Visual and document checks

Minimal uses an oversized editorial title, explicit project subtitle, and open party/table hierarchy. Business uses formal seller/customer blocks and a dark structured header. Subscription uses an asymmetric vertical rail with period, usage, and payment-reference hierarchy. Every page repeats identity, parties, column labels, invoice number, and page count. The last page contains line 72, subtotal `7,200.00 USD`, tax `1,440.00 USD`, total `8,640.00 USD`, notes, terms, and legal fields. This is digital layout evidence, not a physical printer or jurisdictional invoice qualification.
